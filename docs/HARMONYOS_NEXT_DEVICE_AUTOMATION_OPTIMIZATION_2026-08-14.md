# HarmonyOS NEXT 自动化优化方案

> 日期：2026-08-14
> 基线：Piora Harmony Automation v0.2.1
> 原则：只把 CI、代码测试或实机测试能够证明的能力写成产品承诺。

## 1. 本轮审计结论

v0.2.1 已具备 HDC/SDK 自动发现、设备枚举、UI 树、截图、点击、滑动、文本输入、按键、应用启动、右侧投屏、独立视觉模型和目标模式。首轮加固优先处理会造成误操作、控制权卡死、配置损坏或持续占用 HDC 的问题。

### 已修复

1. **投屏背压与取消**：投屏从固定 `setInterval` 改为上一帧完成后才调度下一帧；页面隐藏、切换设备或卸载时中止请求。失败采用最高 8 秒的指数退避。
2. **画面与设备代次绑定**：投屏通过 `fetch + Blob URL` 读取响应中的 generation/revision。只有画面 generation 与当前设备一致时才允许坐标点击或滑动，避免用重连前的旧画面操作新状态。
3. **UI 引用执行前复核**：所有写操作开始时废弃缓存 UI 引用。`tap_ref` 在执行前重新获取 UI 树，严格核对类型、资源 ID、可见标签、可用状态和位置；目标改变或出现多个匹配时返回 `STALE_SNAPSHOT`。
4. **离线租约回收**：设备变为 offline/unauthorized 时立即释放租约并取消后续写入，不再等待五分钟 TTL。
5. **配置事务化**：新 HDC 后端先实际执行只读设备枚举，成功后才写配置和替换现有后端。不存在、损坏或无法执行的候选不会污染下次启动配置，也不会中断当前可用后端。
6. **降低 HDC 压力**：设备静态信息与 UiTest capability 按在线连接缓存；UI 设备发现改为单请求、非重叠的五秒轮询。
7. **手动控制恢复**：手动 owner identity 在当前窗口 session 内稳定保存；刷新后可重新取得同一租约 token。页面隐藏/卸载时使用 keepalive 尝试释放租约。
8. **能力感知 UI**：截图、UI 树、按键、文本输入、启动应用及滑动控件按照设备实际 capability 禁用，停止对不支持功能的重复请求。
9. **视觉输入边界**：运行时再次确认所选模型支持图片；只接受有效 PNG，并限制为 12 MiB、2000 万像素。观察文本限制长度并以不可信数据边界交给操作模型。
10. **请求生命周期**：设备枚举和手动 acquire 都绑定 HTTP `request.signal`，客户端离开后不会在队列尾部迟到并意外取得控制权。
11. **屏幕提示注入与坐标动作收口**：UI 树和视觉模型输出使用显式不可信数据标签并转义边界字符；AI 坐标点击、滑动必须携带 fresh snapshot 的设备 generation。优先使用执行前复核的 `tap_ref`，敏感或语义不明目标不允许依赖坐标猜测。
12. **统一现有会话**：0.2.2 取消独立 `device-control` 切换，普通会话直接加载 `harmony_device`，设备面板、HDC 配置和 Agent 共用一个桌面服务；旧设备模式会话与配置会迁移到统一 normal 运行时。

## 2. 建议的下一阶段

### P0：实机兼容性矩阵

至少选取两代 HarmonyOS NEXT 手机和当前 DevEco SDK，逐项记录：HDC 授权、UiTest 版本、截图格式、UI 树完整度、中文/Emoji 输入、系统弹窗、第三方自绘界面、锁屏/息屏恢复。任何未经该矩阵验证的型号只能标记为“实验性”。

### P1：低延迟投屏后端

当前投屏是经过 HDC 拉取的离散 PNG，可靠但不是视频。若要达到 15–30 FPS，需要单独评估官方投屏协议或已获再分发授权的组件，并放在独立 worker 中。不得把未经授权的 HOScrcpy 二进制直接打入 EXE。

### P1：结构化操作审批

现有 Agent 首次取得控制需要确认，但本地策略无法可靠识别第三方 App 中的支付、发送、删除或授权按钮。建议新增专用 `harmony_action_approval` UI，显示 fresh UI 节点、局部截图、动作哈希和超时；语义不明的坐标点击默认要求确认。

### P1：设备 worker 隔离

HDC/UiTest 长时间运行、进程崩溃和设备拔插应由受监督 child worker 承担；主 Next 进程只保留窄 RPC。Windows 端使用 Job Object 终止整个子进程树，并对 worker 做启动退避和健康检查。

### P2：视觉观察质量评测

建立脱敏截图数据集，分别测量控件召回、坐标误差、敏感页面识别和提示注入抵抗。视觉模型输出只能作为感知提示；最终点击仍以 fresh UI 树或用户确认为准。

### P2：目标模式恢复

目标模式应把 objective、成功条件、证据、checkpoint 和终止原因持久化到 session entry。恢复时必须重新建立设备 lease、重新截图，不允许沿用重启前的 UI ref 或坐标。

## 3. 发布 Gate

每次设备自动化发布至少满足：

- Ubuntu/Windows 的 typecheck、lint、完整单测均通过。
- Windows 打包后 standalone 隔离启动通过。
- 无效 HDC 配置不落盘；离线设备无残留租约。
- 写操作后旧 ref 恒失效；fresh tree 不匹配时不会发出点击。
- 隐藏页面不持续截图；慢截图不会产生重叠请求。
- 打包产物不包含未审计的设备代理或投屏二进制。
- 用至少一台真实授权设备完成截图、UI 树、点击、输入、拔插恢复和急停验收。

## 4. 仍然存在的技术边界

- fresh tree 与实际点击之间仍有毫秒级 TOCTOU，不能称为设备端原子操作。
- 自绘 Canvas/WebView 可能没有可用 UI 节点，只能依赖视觉和更严格的人工确认。
- HDC/UiTest 是开发者授权测试通道，不等同于面向任意零售设备的无授权控制能力。
- 当前 PNG 投屏优先可靠性和可审计性，不承诺视频级帧率。
- 本轮没有连接用户的真实手机，因此“具体型号兼容”仍是发布后的实机验收项。
