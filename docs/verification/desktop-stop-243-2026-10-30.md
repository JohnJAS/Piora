## Bash 复测时间线

以 `.verification/desktop-e2e-lMiFiy/stop-evidence.json` 中 `stopClickedAt` 为零点：

- +123 ms：`cancel_prompt_submission` 返回 HTTP 200，回执 `accepted: true`、`status: cancelled`。
- +309 ms：原 Bash PID 5192 已退出，发送按钮可见、停止按钮不可见；`sleep.exe` PID 26752 仍存活。
- +3,074 ms：发送按钮仍可见，sleep 仍存活；同期服务端 `state.runtime` 为 `idle`，`activeTools` 为空。`running: true` 仅表示 wrapper 仍存在，不能将它单独当作执行状态。
- +29,327 ms：sleep 进程才退出。
- `shell.completed` 不存在，说明被结束的 Bash 没有继续执行后续标记语句；这并不意味着其 sleep 子进程已经被取消。

`false-idle.png` 显示工具卡片“已取消”、聊天“已停止生成”和恢复后的发送入口；必须结合 PID 证据解读，截图本身不能证明后台进程存活。

## 排查方向

当前 SDK 的 Windows `killProcessTree()` 使用 `taskkill /F /T /PID`。本次 Bash PID 是 5192，但实际 sleep 的 Windows ParentProcessId 是 22264，不是 5192。另一次底层探查也观察到 MSYS 中间进程导致的 Windows 父子关系差异。这与外层 Bash 被结束、sleep 遗留的现象一致；后续应排查 Windows/MSYS 进程树清理，不能只调整前端按钮。

测试用发送前后的 Windows `sleep.exe` PID 差集识别子进程，并要求恰好一个新增进程；并行运行其他 sleep 会使归属不可靠，因此本场景应独占运行。进程探查仅读取 PID，不主动结束探查到的进程。

## 修复与复测

通过现有 postinstall 的 Pi source profile，对 SDK 1.4.0 的 `core/tools/bash.js` 应用严格限定、可逆的补丁。Windows MSYS/Cygwin Bash 执行前在独立临时目录记录当前 MSYS PID；取消/超时先从所选 shell 同一安装目录的 `ps.exe` 获取 MSYS 父子关系，再把本次命令对应的 Windows PID 交给 System32 的 `taskkill /F /T`。不按名称清理，不影响其他任务的 sleep。`exec` 替换 Windows PID 时继续使用该执行的 MSYS 身份。

SDK 等待这次清理后才结束执行，并删除临时目录。正常完成的后台任务不在清理范围。保留原 shell 路径、命令前缀、输出格式、权限链及工具元数据；PowerShell 和非 MSYS shell 不启用新增清理。完整补丁必须与仓库文本匹配；逆向恢复的原始文件仍须通过官方 SHA-256 与整棵源码树完整性验证，删除补丁也会使产物验证失败。
